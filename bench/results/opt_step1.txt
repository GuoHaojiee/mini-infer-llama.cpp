## What changed (see docs/stage6.md for the full explanation)

1. Weight scale conversion: hardware F16C (vcvtph2ps), defined in
   quant_avx2.cpp with a matching target attribute so it actually inlines
   into the caller (verified by objdump below) -- no more per-block
   function call. Falls back to a 65536-entry lookup table
   (mi_fp16_to_fp32_lut) on a hypothetical AVX2-without-F16C machine.
2. Activation-side quantization stores the scale as a plain float
   (block_q8_0_act, new MI_TYPE_Q8_0_ACT tensor type) instead of round-
   tripping through fp16 -- mul_mat's Q8_0 path now dots a block_q8_0
   weight row against a block_q8_0_act activation row, so there is only
   ONE fp16->fp32 conversion per block left (the weight's), not two.
3. Row-level accumulation: one __m256 accumulator for the whole row; each
   block's 8 int32 partial sums (not horizontally reduced) are converted to
   float, scaled by that block's dx*dy, and FMA-accumulated lane-wise; a
   single hsum_ps combines the 8 lanes once, at the end of the row, not
   once per block.

mi_vec_dot_q8_0_q8_0 (both operands block_q8_0, fp16 scale) is kept,
identically optimized, purely because tests/test_quant.cpp exercises it
directly; mul_mat itself now calls mi_vec_dot_q8_0_wact instead (see
quant.h's doc comments).

## 2. objdump: mi_vec_dot_q8_0_wact_avx2_f16c (the new hot function)

  objdump -d --no-show-raw-insn -C build/.../quant_avx2.cpp.o

  - 0 `call` instructions in the entire function body (step 0's
    mi_vec_dot_q8_0_q8_0_avx2 had 2 per block).
  - 1 `vcvtph2ps` instruction, inlined directly into the per-block loop
    (confirms the F16C conversion is now a single hardware instruction, not
    a function call).
  - Horizontal sum (vmovaps/vextractf128/vaddps/vmovshdup/vaddps/vmovhlps/
    vaddss) appears exactly once, after the loop -- not per block.
  - Full per-block loop body, straight line, no calls:
      vmovdqu (load weight qs) / movzwl (load weight d, 2 bytes)
      vmovdqu (load activation qs+float d together, 4-byte aligned)
      vpsignb x2, vpmaddubsw, vpmaddwd   (int8 dot -> 8x int32, stage 4's technique)
      vcvtdq2ps                          (8x int32 -> 8x float)
      vmovd + vcvtph2ps + vmulss         (weight fp16 scale -> float, x activation's float scale)
      vbroadcastss + vfmadd231ps         (row accumulator update)

## 4. tools/bench_memread: AVX2 sequential-read-and-sum bandwidth ceiling

(New tool per user request: memcpy's read+write traffic understates the
ceiling for a read-dominated workload like Q8_0 decode -- 6-thread decode
was already measured above memcpy's reported GB/s.)

  $ build/tools/bench_memread $((2*1024*1024*1024)) <n_threads> 15
  n_threads=1  effective_GBps=27.7963
  n_threads=2  effective_GBps=40.0560
  n_threads=3  effective_GBps=43.2409   <- peak
  n_threads=4  effective_GBps=41.2234
  n_threads=5  effective_GBps=35.8585
  n_threads=6  effective_GBps=32.8419
  n_threads=8  effective_GBps=29.9124
  n_threads=12 effective_GBps=26.7761

Read bandwidth peaks at 3-4 threads (~41-43 GB/s) then *declines* with more
threads -- this machine's memory controller saturates well before all 12
logical CPUs are busy; adding more threads past the peak adds contention,
not throughput. This is a materially different shape than memcpy's ceiling
(tools/bench_memcpy.cpp), which plateaus around 14-16 GB/s from 2 threads
up (that number double-counts as read+write bus traffic for a read-mostly
workload like Q8_0 decode, per the user's correction -- kept for the
record, no longer treated as "the" ceiling).

   1 warmup + 5 repeats, mini_infer --bench) -- see opt_step1.csv for raw data

| 1 | 15.407 (stage 4/5 baseline) | 33.832 | 2.196x | 17.97 |
| 6 | 33.139 (stage 4/5 baseline) | 43.052 | 1.299x | 22.86 |

(step 0 baseline numbers are stage 4/5's own bench_quant.py results, same
machine, same GGUF, reused rather than re-measured, since step 0 did not
touch any kernel; step 1's own decode measurement uses this session's
mini_infer --bench with the same n_ctx/prompt_len/decode_len as
bench_quant.py's methodology for a fair before/after comparison.)

1-thread decode's effective bandwidth (17.97 GB/s) is now approaching
1-thread's read-only ceiling (27.80 GB/s, section 4) -- much closer to
memory-bound than step 0's 8.91 GB/s kernel-level number was. 6-thread
decode (22.86 GB/s) is still well below the 3-4-thread read-bandwidth peak
(~41-43 GB/s) -- most of that gap is not going to close by making the
kernel faster still, since 1-thread kernel throughput is already close to
1-thread's own bandwidth ceiling; the remaining 6-thread gap points at
threading/barrier overhead (see docs/stage6.md's step-0 barrier count
finding: 40.9% of barrier_wait calls in a decode step do zero work) as the
next lever, which is what step 3 targets.
